# OI-015: intended intervention versus effective experiment

Campaign: `1ae27a27-6880-4ca6-9d50-e6498e771cb7`. Operations T16 (I14) and T17 (I15).
Analysis date: 2026-10-09. Read-only audit of archived artifacts and Git history.

## Conclusion

T17 was not an independent experiment. Its training produced the same learned
state as T16, step for step, although the two runs used different scientific
source. The campaign nevertheless recorded two training operations, two matched
evaluations and two inquiry closures, and then rejected the distance-envelope
control design on the strength of the second one.

The harness root cause is that the lifecycle identifies an intervention by its
**source delta** and never by its **runtime effect**. A changed file is accepted
as a changed experiment. Nothing in the pipeline observes whether the changed
code path was exercised, and the one artifact that would have exposed the
duplicate was hidden by the existing fingerprint definition.

## Established facts

### 1. The two recipes differ substantively

`robot_learning/scenario/policy_io.py` changed between `ba2e90f` (T16) and
`9988ffc` (T17). The change replaced a fixed damping term with a
distance-derived velocity envelope, and altered every constant that governs it.

| Element | T16 | T17 |
|---|---|---|
| Braking window | `0.01 < d <= 0.055` | `0.012 < d <= 0.050` |
| Folded sector (degrees) | `-165 .. -105` | `-155 .. -125` |
| Trigger | `radial_velocity < -0.05` | `v < -sqrt(2 a gap)`, `a = 1.5` |
| Gain | `RADIAL_APPROACH_DAMPING = 2.0` | `RADIAL_VELOCITY_GAIN = 1.2` |
| Extra terms | none | terminal taper, overshoot gain |

No value survives unchanged. Any activation of the control law would produce a
different action in the two runs.

### 2. The two runs are operationally comparable

Both are `initialization: transfer` from `T3:checkpoint-120832`, seed `0`,
120,000 requested steps, 120,832 completed steps. The Runner recorded distinct
`scientific_commit` values and distinct changed-file fingerprints for each.

### 3. The learned state is byte-identical

At all 24 archived checkpoints, and verified here at `checkpoint-120832`:

| Artifact member | T16 vs T17 |
|---|---|
| `policy.pth` | identical |
| `policy.optimizer.pth` | identical |
| `pytorch_variables.pth` | identical |
| `vecnormalize.pkl` | identical |
| `model.zip` (`data` member) | different |
| `policy_runtime.pkl` | different |

The identical `vecnormalize.pkl` is the strongest single item. Those statistics
accumulate over every observation of all 120,832 steps. Their equality
establishes that the observation stream was identical throughout training, not
merely that the final weights converged to the same point.

### 4. The pipeline can register a `policy_io.py` change

Terminal `policy.pth` digests, same campaign, same checkpoint index:

| Run | `policy.pth` (first 16 hex) |
|---|---|
| T13 | `24228453600dc673` |
| T14 | `4fefcfce47be4aee` |
| T15 | `4c24422d72c83552` |
| T16 | `40c2850ab162140b` |
| T17 | `40c2850ab162140b` |

T15 changed only `policy_io.py` relative to T14 and produced different weights.
The transport path from source to training behavior is therefore working. The
T16/T17 equality is not a delivery failure.

### 5. The T17 module was loaded by the training process

`policy_runtime.pkl` is exported by `robot_learning/train.py` at the end of the
same process that ran the training loop. It serializes the live `PolicyIO`
callables by value. The T16 and T17 files differ in size and content, so the
training process held the T17 function object.

## Inference

Items 1, 3 and 5 are jointly satisfied only if the conditional branch inside
`action_with_prearrival_velocity_shaping` was never taken during training, in
either run. Both action functions returned the policy's action unmodified at
every step, so both runs reduce to the same unmodified transfer recipe.

The remaining logical alternative is that the branch fired in both runs and
produced identical post-clip actions at every step despite different constants
and a different formula. Given the magnitude differences this is rejected as
implausible, though the archived data do not exclude it formally.

**Not established:** why the gate never fired. The conjunction requires a target
in a narrow angular sector, a folded inverse-kinematic branch, a distance inside
the window, and an approach speed above the threshold. The lab artifact
`python-module-M27-*-residual-margin.json` shows `selected_branch: "folded"` in
T3 failure states, so the conjunction is not obviously unreachable. Separating
an unreachable conjunction from a sign, index, or unit defect requires an
activation measurement that was never performed. This audit identifies the gap;
it does not close it.

## Root cause

### Primary: the record proves authorship, not effect

`mechanical_provenance` captures `code_parent_commit` and a fingerprint of each
changed file. That establishes that the PI wrote different code. It cannot
establish that the different code ran, or that running it changed anything. The
lifecycle treats the two as equivalent, so a null-effect intervention is
indistinguishable from an effective intervention that failed.

### Contributing: the existing fingerprint conceals the duplicate

`repository.artifact_fingerprint` hashes raw file bytes of the archived
artifact. `model.zip` carries per-entry timestamps and a `data` member that
embeds the serialized configuration, and `policy_runtime.pkl` embeds the
scientific source. All three differ between T16 and T17 while the learned
parameters do not. Every fingerprint the Runner computes therefore differs, and
the duplicate is invisible at exactly the point where it is cheapest to detect.

### Consequence: a false negative steered the campaign

I15 closed against a recipe that was never exercised. E63/E64 rejected the
distance-envelope design and moved to a different terminal-state representation.
One full training allocation (120,832 steps) and one 160-episode matched
evaluation were spent producing evidence about nothing, and the resulting
negative conclusion redirected the remaining campaign.

This is distinct from OI-014. OI-014 concerns a bundled change receiving a
single-cause explanation. OI-015 concerns a change with no effect receiving any
explanation at all.

## Proposed repair

Three bounded parts. None of them makes a scientific judgment.

### A. Runner: a learned-state fingerprint

Add a digest over the learned parameters only: the uncompressed `policy.pth`,
`policy.optimizer.pth` and `pytorch_variables.pth` members of `model.zip`, plus
`vecnormalize.pkl`. Exclude zip metadata, the `data` member and
`policy_runtime.pkl`.

Hook: `runner/run_experiment.py`, after `archive_candidates` and before the
training `result` is assembled. Cost is a digest over about 155 kB per
checkpoint.

### B. Runner: report an exact duplicate as an observation

When a completed training operation's learned-state fingerprints match those of
an earlier completed training operation in the same campaign, record the fact in
the training result, for example `duplicate_learned_state: "T16"`. Surface it in
`campaigns/brief.md` beside the existing provenance line.

The Runner reports the match. It does not block the operation, reject the
candidate, rate the intervention, or suggest what to do. This keeps the Runner
mechanical.

### C. `contracts/program.md`: the interpretation rule

State that a completed training operation whose learned state duplicates an
earlier operation does not establish an independent test of the intended change,
and that the PI resolves why before treating its measurement as evidence about
that change. Resolution stays a PI choice: an activation measurement, a
redesigned gate, or a recorded limitation.

## Expected behavioral gain

| Without the repair | With the repair |
|---|---|
| T17 completes, M28 runs 160 episodes, I15 closes negative, the design is rejected | The duplicate appears at T17 completion, before M28 |
| The record shows two independent experiments | The record shows one effective experiment |
| 120,832 steps plus one evaluation produce no information | The allocation is still spent, but the PI learns the gate is inert |
| The campaign abandons a route on untested evidence | The PI can probe activation and keep the route open |

The repair does not prevent the wasted training run. It prevents the wasted
run from being promoted into a false scientific conclusion.

## Limits

- Byte-identical learned state is **sufficient** evidence of an inert change,
  not **necessary**. A nearly inert change produces different weights and will
  not be detected. The repair catches the exact-duplicate case only.
- Detection requires comparable runs. Two runs with different seeds or different
  parents will not produce identical weights even if both interventions are
  inert, so the signal is silent there.
- The repair does not explain why a given gate fails to fire. That stays a
  scientific question on the PI surface.
- The T16/T17 activation question remains open. Answering it needs an authorized
  measurement, which this audit does not perform.

## Rejected alternatives

- **A Runner gate that refuses the operation.** It would require the Runner to
  decide that a result is scientifically worthless. The Runner does not judge.
- **A required activation counter in `policy_io.py`.** It prescribes scientific
  method inside the PI-owned surface.
- **Static source or AST comparison.** A different syntax tree says nothing
  about runtime effect, which is the whole defect.
- **Automatic re-run with a different seed.** It spends a second allocation to
  answer a question the PI may not consider decision-relevant.

## Boundary

No campaign was launched, resumed, reset, trained, measured or evaluated for
this report. All findings come from archived campaign artifacts and read-only
Git history. No harness, policy, training recipe or campaign record was changed.
