# RCA: campaign stopped after scientific coding, 13 October 2026

## Finding and confidence

**Confirmed failure mechanism:** Copilot rejected the parent PI's next model request after a successful native coding handoff. The detailed error is `invalid_request_body`, with `type=websocket_error`, in `errorContext=model_call`. The HTTP-style status reported by the runtime is 400. The console's wording, “internal server error,” hides this useful classification.

**Underlying root cause remains unproven.** The saved evidence does not contain the rejected outbound request body or a server explanation identifying its invalid field. It cannot establish whether the defect was in native-runtime request construction, WebSocket conversation state, provider processing, or a particular combination of those with the harness integration. A deterministic regression and an intermittent runtime/provider defect both remain possible.

The strongest recent *regression candidate* is commit `764b69f`, which introduced native coding tasks and upgraded the SDK. It is not a demonstrated culprit. Three earlier handoffs in this same campaign succeeded through the same mechanism. There is no justification for declaring this random, but there is also no evidence sufficient to declare a specific recent commit causal.

## What failed, and what did not

`read_agent` is a runtime-generated exchange here. Its assistant event lacks the model-response metadata present on normal model-generated calls, and its request, execution and completion all occur at the notification timestamp. The repository adapter contains no direct `read_agent` invocation. It starts the native task through `session.rpc.tasks.start_agent`, then waits for its result.

The actual source change and structured handoff succeeded. The two new files existed, and the returned manifest recorded 14,512 and 16,107 bytes. `check_executed=false` and `review_required=true`: completion meant authoring finished, not that the new code had been validated. Neither proposed check had been submitted in S5.

The PowerShell line in the user's excerpt is a downstream assertion. [copilot_controller.ps1:309](C:/Users/cyril.beurier/code/robot-learning-inquiry-centered-lifecycle/runner/copilot_controller.ps1:309) throws when the adapter returns a nonzero exit code. It does not construct the rejected model request.

The adapter's [error handler](C:/Users/cyril.beurier/code/robot-learning-inquiry-centered-lifecycle/runner/copilot_adapter.py:1652) reports only `data.message`. This is a confirmed observability limitation: the console omits the structured status and correlation fields, while the useful inner error remains in the native event log. It obscured diagnosis but did not cause the 400.

## Root-cause boundary and next discriminating work

The established chain is:

```text
successful coding and handoff
    -> native idle notification + successful read_agent
    -> next parent model request rejected over WebSocket
    -> SDK session.error
    -> adapter failure outcome
    -> PowerShell stops campaign
```

The unresolved boundary is between the native runtime's request construction/conversation state and the provider's request processing. The local native-runtime package is compiled; the inspected process log and event history do not preserve the rejected outbound body or name an invalid field. No identical-input replay or controlled transport comparison was performed, so deterministic reproduction has not been demonstrated.

The next useful work is a small, isolated harness reproduction, with no training or campaign writes:

1. Capture request/error diagnostics around a native-task handoff, preserving model, SDK/runtime versions and tool schemas. Use harmless fixed results and include a result comparable in size to this one. Compare with an equivalent tool result without a native child.
2. Compare WebSocket and HTTP Responses transport with the same setup. The installed SDK explicitly supports `capi={"enable_web_socket_responses": False}` in both session creation and resume. This is an available diagnostic control, not a validated fix.
3. If a stable failure reproduces, bisect the native-task integration separately from the SDK/runtime change. Do not conflate these two changes by rolling back both and calling the result proof of either one.
4. Preserve structured error context and request identifiers in harness diagnostics. Do not add blanket retries around coding or operation submission: those can repeat already completed work and would conceal the cause.

Upstream [Copilot CLI issue #2543](https://github.com/github/copilot-cli/issues/2543) reports a different subagent/history corruption failure. Its CLI version, model, compaction conditions and orphaned-tool evidence differ from this incident. It establishes a relevant class of historical failures, not a diagnosis of this one. No matching upstream fix was verified.
