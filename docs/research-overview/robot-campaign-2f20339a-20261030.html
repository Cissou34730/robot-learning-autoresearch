Why T1 failed, and what the PI changed

What M1 showed

  • T1 failed 108 of 400 episodes.
  • 104 of the 108 failures had a target closer than 14 cm. This includes all 20 hold failures and all 25 large reach misses.
  • The inherited recipe trains only on targets from 14 to 20 cm. The official task uses 6 to 20 cm, a range 2.3 times wider.
  • 3 of the 4 other failures were in a 20° zone where the selected elbow solution hits a joint limit.
  • The training score was still rising at 120,000 steps.

The two changes in T2

  1. Training targets. The training range is now 6 to 20 cm, the same as the official range. Before, it was 14 to 20 cm.
  2. Observation. The old observation gave the policy two joint-angle solutions for the target. The new one gives only the solution that respects the joint limits. That is the solution with the smaller shoulder angle. The observation has 9 values instead of 11.

The PI kept direct motor torque output, the PPO network (64×64, tanh) and the inherited reward.

Code commit 2a4f201a in the campaign repository changed robot_learning/scenario/observations.py and robot_learning/training/environment.py (16 lines added, 8 removed). The scenario forbids inverse kinematics only in the output transformation. The PI can build the observation freely, so this change obeys the rules.

How good is the T2 policy?

On M3 (400 new episodes) the policy succeeded in every case:

  • Every 2 cm distance group from 6 cm to 20 cm: 100%.
  • Every 30° direction group: 100%.
  • Every episode held the target for the full 100 steps.
  • The arm first reached the target between step 5 and step 15.
  • The largest final distance to the target was 0.877 cm. The tolerance is 1 cm.

Problems before this run

We stopped the first DeepSeek runs because of two harness bugs. Both are now fixed:

  1. The coder had no file editor. A coder sub-agent gets only the editors that its model and the PI model both allow. With a DeepSeek PI and a GPT coder, that set was empty.
  2. The coder could not create a file in a new folder. The create editor does not make missing folders. The harness now makes the folders before coding starts.

Open point: the coder OI-063

With an OpenCode PI, the coder now runs on the same model as the PI. The reviewer stays on gpt-6-luna. This is a temporary solution. The maintainer is not satisfied with the coding part.

OI-063 tracks the real fix. There are two options:

  • a harness file editor tool that every model can use, or
  • a separate coder session on a Copilot model.

Conclusion

  • A full campaign with an OpenCode model works from start to official assessment.
  • The PI found a direct cause in the first measurement and fixed it in one step.
  • The coder setup for OpenCode PIs stays temporary until OI-063 is fixed.
