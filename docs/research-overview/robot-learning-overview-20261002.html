02 / IMPLEMENTED PROCESS / THE CAMPAIGN LOOP

Current runtime and scientific-session boundaries

A campaign can contain several inquiries. An inquiry can contain several training runs and measurements.

Startup does not require training

The PI can build tools, change its method, or measure before training.

A startup training request can be shorter than the maintainer's allocation. It cannot be larger.

Inquiry training still uses the full allocation. Completed steps can round up at a rollout boundary.

Current goal-review behavior

Closing an inquiry does not mean campaign success.

A development score above the goal does not automatically justify assessment.

The PI decides whether evidence justifies assessment. The Runner checks the operational contract, not scientific adequacy.

Goal review can measure. Its permissions do not depend on the inquiry count. It does not train.

The temporary inquiry cap does not establish scientific exhaustion.

An official failure ends the campaign. It does not automatically return to another inquiry.

The additional readiness prompt from e4736da is withdrawn. Its former guidance appears only in the history below.

Goal, campaign, inquiry, session, operation, and AI invocation are different units
Human goal
The fixed task and success criterion. Lower-level milestones do not replace it.
Campaign
One attempt to reach the goal. It starts with independent records and a new scientific model.
Inquiry
A temporary question that can change the route to the goal. It has a question, goal connection, and closure condition.
Scientific session
Work on one coherent objective. It can include several operations. A scientific session record or terminal goal-level decision ends it.
Operation
One accepted request, such as measurement, training, or publication of the scientific session record through checkpoint.
PI invocation
One call to the AI backend. Several invocations can belong to the same scientific session.

A completed training run is not automatically a completed session, inquiry, or campaign.

Continuation, reframing, closure, and the inquiry limit

Continue: keep the inquiry open and save the scientific session record. A fresh session continues the same question.

Reframe: change the active question and its connection to the goal. Save the scientific session record before further work.

Close: record the outcome and reason. After the scientific session record is saved, return to goal review.

Inquiry closure can follow a useful answer, a changed direction, or rejection of that inquiry's route. It does not establish campaign exhaustion.

The current 15-inquiry cap is a temporary execution limit, not a scientific decision signal.

After the final permitted inquiry closes and saves its scientific session record, the launcher pauses without a terminal state. Active work finishes normally.

The maintainer can resume by an explicit increase of -MaxInquiries at that paused boundary. Measurements and model-role permissions do not change. Assessment still requires an explicit best-known candidate.

Later cap removal is a deferred maintainer decision, not part of the current runtime. See the backlog.

03 / CURRENT CONTRACT / RESPONSIBILITY AND OWNERSHIP

The human owns the goal. The PI owns the science. The Runner operates the process.

Human

Defines the goal, robot, protected task, and success rule.

Maintains the harness and sets operational limits.

Starts, stops, and resets campaigns.

Principal Investigator / PI

Chooses questions, methods, and tools.

Changes PI-owned research code.

Interprets completed evidence.

Decides whether to request assessment.

Runner

Checks contracts and file ownership.

Executes accepted operations.

Records outcomes and artifacts.

Does not judge scientific readiness.

The human can also maintain the harness. Maintainer is an engineering function, not a fourth campaign actor.

The two environment files are both PI-owned

The split separates shared research mechanics from training-specific code. It is not a human/PI ownership split.

These code paths are under robot_learning\. Protected exceptions take precedence over PI-owned directories.

PI freedom remains inside the scientific boundary

The PI can replace its methods, tools, reward, observations, and training implementation.

It cannot change the official robot, task, success rule, harness, tests, or dependency manifests.

All Python execution uses uv run. The PI uses Runner requests for training and protected evaluation.

04 / IMPLEMENTED PROCESS / THE OPERATION LOOP

From a PI request to a recorded result

The launcher resumes pending work before it asks for another action. The Runner executes requests. The PI interprets the results.

StepActionRecord or boundary
1. PrepareThe PI chooses an action and states its scientific reason. It can change PI-owned code or build a tool.Changes must remain within the owned surface.
2. SubmitThe PI writes one operation to research\operation_request.json.The request has one top-level operation kind.
3. ValidateThe Runner checks shape, phase permissions, ownership, allocation, and instrument-specific conditions.A structurally valid request is not a scientific endorsement.
4. AcceptThe Runner saves the accepted request as a pending operation and assigns its identity.Accepted request identity is fixed during execution. M# means measurement, T# training, and E# another event.
5. ExecuteThe Runner executes the instrument or requested state transition.Training produces candidates. Measurement produces factual outputs and detailed artifacts.
6. PublishThe Runner saves outcomes, provenance, artifacts, and operation history.Use only completed operations as scientific evidence.
7. ReturnThe launcher regenerates the brief and returns feedback to the PI.The PI inspects evidence and decides the next action in the same session.
What happens when the operation does not complete normally
SituationProcess responseScientific meaning
Invalid requestReturn the validation reason. The launcher permits one correction retry, then stops if the request remains invalid.No accepted scientific result exists.
Scientific-code execution errorPreserve pending state and return the error to the same PI session. The PI can repair the implementation or explicitly replace the failed operation.The exception is execution history, not a measurement against the method.
Publication failure after executionPreserve the result and pending transaction. Stop for publication repair. Resume publication rather than retraining.Do not confuse a produced result with a new training request.

A completed method can perform poorly and still provide useful evidence. A code exception is a different situation.

Startup allocation and inquiry allocation

The maintainer supplies a per-run training allocation. The default is 120,000 requested steps.

During startup, the PI can request any positive step count up to that allocation.

During an inquiry, a training request must use the full allocation.

Neither phase requires training. Neither the PI nor the Runner can raise the maintainer's allocation.

Completed steps can round up to a learning rollout boundary. The ceiling controls the request, not strict executed-step stopping.

Candidate and recipe are different

Standard candidate publication depends on training. Training produces registered learned-policy candidates.

A controller artifact created during measurement is not automatically a registered candidate.

A recipe is the scientific code and configuration associated with that candidate.

Recipe restoration changes the PI-owned recipe. It does not assign a model role.

Training statistics can identify candidates worth inspecting. They do not establish development or official performance.

Model roles require explicit assignment

Working: the candidate selected for current work.

Best-known: the strongest available candidate supported by completed evidence.

Retained: a candidate archived under an explicit label.

Training does not assign these roles automatically. Best-known assignment does not require official assessment.

What the scientific session record must preserve

The scientific session record states the connection to the human goal and the remaining gap.

Its synthesis distinguishes measurements from explanations. It retains supporting and contradictory evidence.

Its decision frontier states the unresolved distinction and the evidence that can resolve or redirect it.

Its next direction states the selected action or closure and the reason.

It also records completed operations, candidate roles, evidence references, and cumulative resource use.

A new session receives this durable context. It does not depend only on the previous conversation.

Development measurement and official assessment

Development measurements inform the PI's judgment. They do not declare the official goal reached.

Matched comparisons use the same episode seeds for the compared candidates.

The protected official panel is separate. Do not combine its result with development scores.

Official assessment requires goal review, no active inquiry, and an explicitly assigned best-known candidate.

The PI decides whether to request it. The Runner checks the operational contract and executes it.

Either official pass or official fail ends the campaign.

Current startup purpose and instruction delivery

Startup establishes or refines a credible initial scientific direction through scientific work. The direction comes from the human goal, physical model, and available evidence.

Startup can build or adapt reusable scientific tools and PI-owned methods. Subsequent inquiries can use these tools and methods. The PI can also use current tools that fit the chosen direction.

The PI chooses the first useful scientific action and explains why it advances the direction. The scientific session record preserves the work and its result.

The record also preserves remaining uncertainty and the selected next action.

The scientific-model phase runs under a robotics and simulation analyst persona. The 5 October goal-first order and robotics-first persona are historical. Commit ef9516f replaced them on 8 October.

Ordinary phase prompts deliberately remain persona-first. Their shared persona directs science toward the scenario goal. It does not make a learned policy the generic role identity. It does not imply a research method.

Ordinary prompts present information in this order:

  1. The human task and protected boundary.
  2. The physical and scientific synthesis.
  3. Completed evidence and its limits.
  4. The goal gap and decision frontier.
  5. The active inquiry and objective.
  6. Decision guidance.
  7. Legal operations and applicable resources.
  8. Source routing and submission mechanics.

The independent R2 review recommended the human goal and task conditions before the PI role. Commit fb9b10d kept persona-first ordinary sessions.

Thus R2 is partially implemented. Goal-first ordinary sessions are the missing part.

The scientific-model phase uses a robotics and simulation analyst persona. The model has three registers and no synthesis section. Startup reads the whole model.

Startup reads pi_workspace\scientific_model.md and contracts\program.md. It selects its own direction from the model, the program, and the human goal.

This direction remains revisable. It is not a first-measurement rule or a procedural question-first rule. The adapter supplies no scientific instruction block.

A scientific session record is not a policy checkpoint. The record preserves actual work, results, remaining uncertainties, and the next action. A policy checkpoint contains saved model weights. The current checkpoint operation and fields remain unchanged.

The preliminary phase can read all scientific sources under robot_learning\. These sources include the protected benchmark implementation. SDK reads and explicit shell reads use this phase distinction. Later phases retain reserved-read restrictions.

Maintainer documents and harness scripts stay reserved in every phase. Read access does not change write authority or direct-execution restrictions. These are tool controls, not OS isolation.

The startup prompt displays the maintainer's requested-step training allocation as a ceiling. It does not require training, measurement, or any other operation, and it adds no scientific-adequacy gate.

10 / CURRENT TERMS AND SOURCE APPLICABILITY

Model and checkpoint terminology

Scientific model
A document about the robot and task. It separates established facts, physical consequences, and unknowns.
Learned policy
The controller produced by learning. It chooses actions from observations.
Policy checkpoint
Saved model weights from a training run. They are not a scientific conclusion.
Scientific session record
A written record of actual work, evidence, interpretation, remaining questions, and next direction. The checkpoint operation saves this record.
Best-known policy
The strongest available candidate supported by completed evidence. It is not automatically ready for assessment.
Harness
The launcher, Runner, contracts, and context that support the research process.
Inquiry
A temporary question that can change the route to the human goal. It is not one training run.
