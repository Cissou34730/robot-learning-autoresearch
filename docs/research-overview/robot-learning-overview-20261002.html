Robot AutoResearch / overview

Robot AutoResearch

Robot AutoResearch is a harness. It lets an independent AI agent, the Principal Investigator (PI), train a robot.

The human owns the goal. The PI owns the science and the training. The Runner is the gatekeeper. It checks and runs every operation.

The working example is a two-joint arm that must reach a target and hold still. Work is organized in campaigns. A campaign is split into inquiries. An inquiry is one scientific question.

2 / ROLES AND BOUNDARIES

Who owns what

Human

Defines the goal, the robot, the protected task, and the success rule.

Maintains the harness and sets limits.

Starts, stops, and resets campaigns.

Principal Investigator (PI)

Chooses questions, methods, and tools.

Changes PI-owned research code.

Interprets completed evidence.

Decides whether to request the official assessment.

Runner

Checks contracts and file ownership.

Runs accepted operations.

Records outcomes and files.

Does not judge scientific readiness.

The maintainer is the human acting as engineer. It is not a fourth role in a campaign.

benchmark\, runner\, tests\, docs\, tools\HumanProtected. A protected path wins over a PI-owned folder.

The PI can replace its methods, tools, reward, observations, and training code.

The PI cannot change the official robot, task, success rule, harness, tests, or dependencies.

All Python runs through uv run. The PI asks the Runner for training and protected evaluation.

The read limits are tool controls. They are not an operating-system sandbox.

4 / HOW A CAMPAIGN RUNS

The campaign lifecycle

A campaign is one attempt to reach the goal. It can hold several inquiries. An inquiry can hold several training runs and measurements.

PhaseWhat happensHow it ends
Scientific modelThe PI reads the robot and task contracts. It writes a model with four headings: Established facts, Physical consequences, Unknowns, and Decision-relevant synthesis.The Runner accepts and publishes the model. It stays fixed for the campaign.
StartupThe PI picks the first scientific direction. It can build tools, change PI-owned code, measure, train, assign roles, or restore a recipe.A session record saves the direction and the work. A fresh goal-review session follows.
Goal reviewThe PI reviews the gap to the goal. It can measure, assign model roles, open an inquiry, or request the official assessment. It cannot train.Opening an inquiry needs a saved session record. Official assessment is the only way to end the campaign.
InquiryThe PI works on one question. It can build, measure, train, assign roles, or restore a recipe. It can continue, reframe, or close the question.The PI saves a session record. Then a fresh session continues, or goal review starts after a close.
EndThe official assessment records a pass or a fail.The campaign ends. A maintainer stop is a different event and gives no result.

Rules for goal review

Closing an inquiry does not mean success.

A development score above the goal does not force an assessment.

The PI decides if the evidence justifies an assessment. The Runner checks only the operational contract.

An official failure ends the campaign. It does not return to another inquiry.

Rules for the inquiry cap

The cap is 15 inquiries. It is a temporary execution limit.

After the last allowed inquiry is saved, the launcher pauses. A pause is not a conclusion.

Only the maintainer can resume, with a higher -MaxInquiries. Removing the cap is OI-013.

From a PI request to a recorded result
  1. The PI picks an action and writes one request to pi_workspace\operation_request.json.
  2. The Runner checks the shape, the phase, the file ownership, and the allocation.
  3. The Runner accepts the request and gives it an id. M# is a measurement, T# is training, E# is another event.
  4. The Runner runs it and saves the result, the files, and the history.
  5. The launcher rebuilds the brief and resumes the PI.

Only completed operations count as evidence. A valid request is not a scientific endorsement.

SituationResponse
Invalid requestThe Runner returns the reason. One retry is allowed. Then the launcher stops.
Error in PI codeThe error goes back to the same PI session. It is execution history, not a scientific result.
Publication failure after a runThe result is kept. The launcher stops for repair. It resumes publication and does not retrain.
Maintainer stopState is kept. It is not a pass, a fail, or a conclusion.
Training allocation
  • The maintainer sets a per-run allocation. The default is 120,000 requested steps.
  • In startup, the PI can request any positive number of steps up to the allocation.
  • In an inquiry, a training request must use the full allocation.
  • Training is optional in both phases.
  • Completed steps can round up to a rollout boundary.
Units: goal, campaign, inquiry, session, operation
Human goal
The fixed task and success rule.
Campaign
One attempt to reach the goal. It starts with a new scientific model.
Inquiry
A temporary question that can change the route to the goal. It has a goal link and a closure condition.
Scientific session
Work on one coherent objective. A saved session record ends it.
Operation
One accepted request, for example a measurement, a training run, or a session record.
PI invocation
One call to the AI backend. A session can have several.

8 / EVIDENCE, MODEL ROLES, AND TERMS

Evidence records and model roles

RecordPurposeLimit
pi_workspace\scientific_model.mdThe physical reference of the campaign.Fixed. Later evidence can correct it only in a session record.
runner\state\research_state.jsonCurrent inquiry, session, pending operation, candidates, and roles.A pending operation is not evidence. It changes with each campaign.
campaigns\results.jsonlThe authoritative history of operations.Failed attempts are execution history, not evidence.
campaigns\evaluations\Detailed measurement files.A summary is not the full file.
campaigns\brief.mdGenerated short context with source references.It does not replace the detailed measurements.
Session recordSaves the synthesis, the evidence, the remaining gap, and the next direction. The stored field is pi_checkpoint.It can be wrong. It must keep contradictory evidence.

Model roles need an explicit assignment

Working: the candidate in use now.

Best-known: the strongest candidate that completed evidence supports.

Retained: a candidate archived under a label.

Training never assigns a role. Best-known does not need an official assessment.

Development and official results

Development measurements inform the PI. They do not declare the goal reached.

Matched comparisons use the same episode seeds.

The official panel is separate. Never mix its result with development scores.

The official assessment needs goal review, no active inquiry, and an assigned best-known candidate.

Terms

Scientific model
A document about the robot and task. It separates facts, consequences, and unknowns.
Learned policy
The controller that learning produced. It picks actions from observations.
Policy checkpoint
Saved model weights from a training run. It is not a scientific conclusion.
Session record
A written record of work, evidence, open questions, and the next direction. The checkpoint operation saves it.
Candidate and recipe
A candidate is a registered learned policy. The recipe is the code and settings that produced it.
Best-known policy
See model roles. It is not automatically ready for assessment.
Harness
The launcher, the Runner, the contracts, and the context that support the process.
Status words
Implemented: in the code. Observation: a result in a named campaign. Open: not solved. Proposal: not approved. Deferred: set aside. Withdrawn: removed. Historical: old, not current.
