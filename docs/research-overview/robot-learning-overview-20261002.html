Robot AutoResearch

Robot AutoResearch lets an AI Principal Investigator (PI) develop and test methods for a robot.

The human defines the goal. The PI chooses the scientific work. Runner checks and executes accepted operations. It does not choose the science.

The example is a two-joint arm that must reach a target and hold still. Training is one tool, not the whole process.

Last reviewed 27 October 2026. This is a static architecture and status overview, not a live campaign monitor. The filename is retained for existing links. The harness tracker is the source for status and issues; this page mirrors its register. Local campaign records establish measured results.

Current agent runtime

One SDK, multiple inference providers

  • Copilot SDK 1.0.26 handles sessions, tools, native coding and independent review. OpenCode Zen/Go are inference routes within that runtime.
  • The default PI is Copilot GPT-6 Luna with high reasoning. Copilot scientific-model preparation uses max reasoning.
  • Reviewers use high reasoning: the selected campaign model for Copilot campaigns, Copilot GPT-6 Luna for OpenCode campaigns. Corrections reuse the same reviewer.
  • The reviewer can read selected files. It cannot edit code, execute checks or choose the scientific direction.
  • The reviewer requests a complete batch of engineering repairs from the same coder. The PI receives the final package or a blocked requirement.
  • The review returns validation, what is wrong, why and where. A missing assertion does not prove wrong measurement output.
  • Unclear requirements and scientific choices return to the PI. Runner does not coordinate repairs. The reviewer does not execute checks.
  • The runtime checks the actual reviewer model and reasoning level. It records reviewer usage separately.
  • Coder, reviewer and PI usage remain separately accounted. OpenCode token/catalogue costs are not invented Copilot AIU.

Run campaigns from the harness folder

Standard: 1 to 5 campaigns at once. uv run python -m tools.run_parallel --count 3 uses campaign-1 to campaign-3, initializes missing slots from an existing one, resets each to the recipe, launches each campaign in the background without a window and starts a monitor that stops a campaign cooperatively at 6 h of active time or 120 AIU (defaults; the PI never sees these caps). Launcher logs and one report per campaign go to %TEMP%\robot-learning\parallel-<time>. Watch and stop campaigns with .\campaign_tui.ps1.

One campaign by hand. .\run_research.ps1 (the Python launcher runner.launcher) launches or resumes the selected campaign without console output. It does not reset it.

uv run python -m runner.launcher.reset --mode fresh --clean --recipe-ref baseline-distinct-episodes-v3-robot --force ; .\run_research.ps1

The second command deliberately resets before launch. Stop the campaign first. --clean discards eligible uncommitted changes. The semicolon is not success-only: inspect any reset failure before authorizing launch.

Both accept --campaign-root <path> and default to campaign-1. They run in their own process, so the caller's folder never changes. A campaign stops cooperatively when its stop request .git\stop-request appears.

Baseline v3 is a recipe, not a trained model. Its Fresh reset keeps the current harness, restores scientific files and starts empty history with scientific-model preparation pending. It does not restore an old harness commit.

The task fingerprints must match. A new campaign repository needs one-time initialization from a source repository containing the recipe tag; tools.run_parallel does this for missing slots, an ordinary reset does not.

2 / HOW IT WORKS: ROLES

Who owns what

Human

Defines the goal, the robot, the protected task, and the success rule.

Maintains the harness and sets limits.

Starts, stops, and resets campaigns.

Principal Investigator (PI)

Chooses questions, methods, and tools.

Defines bounded code changes.

Reviews code, proposed checks and independent review findings.

Interprets completed evidence.

Decides whether to request the official assessment.

Runner

Checks contracts and file ownership.

Runs accepted operations.

Records outcomes and files.

Does not judge scientific readiness.

The maintainer is the human acting as engineer. It is not a fourth role in a campaign.

The PI can replace its methods, tools, reward, observations, and training code.

The PI requests code changes in exact selected files. A native coder receives the request and selected context, not the campaign conversation.

An independent read-only reviewer examines each assignment. It requests engineering repairs as one batch. The same coder makes the changes. The same reviewer checks them.

The PI receives the final package or a blocked requirement. Scientific decisions remain with the PI. Neither helper executes checks or submits operations.

Runner executes the checks that the PI requests. Code review does not approve scientific conclusions.

The PI cannot change the official robot, task, success rule, harness, tests, or dependencies.

Ordinary Copilot main and coding sessions have no shell tools. The main PI calls submit_operation without file-write tools.

The preliminary phase keeps its scientific-model publication permission and phase-specific tools. Runner executes scientific checks, training and evaluation using the harness environment.

Copilot SDK 1.0.26 supplies agent lifecycle, custom tools and native subagents for Copilot and OpenCode inference. OpenCode adds a scoped read alias; it is not a separate legacy TypeScript runtime.

The PI chooses complete evidence or scoped queries through artifact_evidence_query and training_log_query. Large results identify continuation. Partial content never appears as complete evidence.

Two optional numeric tools compute values without judging claims. training_series_statistics summarizes one training metric over a step window and evaluates thresholds that the PI chooses. success_rate_pass_probability estimates the probability that a candidate reaches a success-rate goal on a new panel, from counts that the PI supplies.

Read-only review uses high reasoning. Max reasoning applies to Copilot scientific-model preparation, not the reviewer. Engineering checks do not establish scientific effectiveness.

The read limits are tool controls. They are not an operating-system sandbox.

2 / HOW IT WORKS: CAMPAIGN LIFECYCLE

The campaign lifecycle

A campaign is one attempt to reach the goal. It can hold several inquiries. An inquiry can hold several training runs and measurements.

Phase What happens How it ends
Scientific model An analyst session, with its own persona and reference in the system message, reads the robot and task definitions and the current recipe. It writes a model with four headings: Established facts, Physical consequences, Unknowns, and Decision-relevant synthesis. The Runner accepts and publishes the model. It stays fixed for the campaign.
Startup The PI picks the first scientific direction. It can build tools, change PI-owned code, measure, train, assign roles, or restore a recipe. A session record saves the direction and the work. A fresh goal-review session follows.
Goal review The PI reviews the gap to the goal. It can measure, assign model roles, open an inquiry, or request the official assessment. It cannot train. Opening an inquiry needs a saved session record. Official assessment is the only way to end the campaign.
Inquiry The PI works on one question. It can build, measure, train, assign roles, or restore a recipe. It can continue, reframe, or close the question. The PI saves a session record. Then a fresh session continues, or goal review starts after a close.
End The official assessment records a pass or a fail. The campaign ends. A maintainer stop is a different event and gives no result.

Rules for goal review

Closing an inquiry does not mean success.

A development score above the goal does not force an assessment.

The PI compares the strongest candidate's evidence with what further bounded work can credibly add, and records the evidence against the chosen alternative. An unresolved mechanism does not by itself require deferral.

The PI decides if the evidence justifies an assessment. The Runner checks only the operational contract.

An official failure ends the campaign. It does not return to another inquiry.

Rules for the inquiry cap

The cap is 15 inquiries. It is a temporary execution limit.

The PI sees only the number of opened inquiries, not the cap. The launcher console shows the cap to the maintainer.

After the last allowed inquiry is saved, the launcher pauses. A pause is not a conclusion.

Only the maintainer can resume, with a higher --max-inquiries. OI-013 is withdrawn: the maintainer did not adopt the removal proposal. The cap remains an accepted execution limit.

From a PI request to a recorded result
  1. The Copilot PI picks an action and calls submit_operation with the request envelope. The exchange file stays internal to the trusted controller and Runner.
  2. The Runner checks the shape, the phase, the file ownership, and the allocation.
  3. The Runner accepts the request and gives it an id. M# identifies a measurement. T# identifies a training run. E# identifies another event.
  4. The Runner runs it, saves the result, the files and the history, and commits them to the local campaign Git repository.
  5. The launcher rebuilds the brief. It returns concise results, errors and changed state to the same conversation. A checkpoint ends that context. The next bounded context is fresh, on the same SDK runtime.

Only completed operations count as evidence. A valid request is not a scientific endorsement.

Situation Response
Invalid request The Runner returns the exact reason directly. Checkpoint list errors identify the current session and both expected and submitted lists. One retry is allowed. Then the launcher stops.
Error in PI code The error goes back to the same PI session. It is execution history, not a scientific result.
Publication failure after a run Runner keeps the result and transaction. The launcher stops for repair. It does not automatically reaccept or retrain.
Lost response Submission stops. On resume, the controller recovers existing pending/completed Runner state instead of blindly replaying the tool call.
Maintainer stop State is kept. It is not a pass, a fail, or a conclusion.
Training allocation
  • The maintainer sets a per-run allocation. The default is 120,000 requested steps.
  • In startup, the PI can request any positive number of steps up to the allocation.
  • In an inquiry, a training request must use the full allocation.
  • Training is optional in both phases.
  • Completed steps can round up to a rollout boundary.

Inquiry
A temporary question that can change the route to the goal. It has a goal link and a closure condition.

4 / WHAT DECIDES SUCCESS

What decides success

Findings from the campaigns of 22 to 26 October, especially the three parallel rounds, where several campaigns started from the same recipe on the same harness. They are observations, not controlled experiments; the tracker holds the details.

Decisive

The arm's reflection symmetry

  • The remaining failures always sat in one angular sector, negative target angles from about −180° to −90°, while the mirrored sector succeeded.
  • Every campaign that used the symmetry (reflected inputs and mirrored motor commands) on a direct-torque policy passed quickly: cfa88359, 6b13d5f4, fecc7566, 17e9764f, de7af8af. 38ad68c6 applied it on a weaker fixed-gain base and did not pass. Every campaign that did not use it stalled at about 97.5%.
  • Before 26 October the analyst's scientific model stated the symmetry in 1 of 28 models; that campaign, 6b13d5f4, passed in 52 minutes. Since the analyst models invariances (OI-053), 6 of 6 models state it. In round 4 (27 October) all three treated it as a consistency check only, none used it in the policy, and none passed.
Method

How the winners reasoned

  • They compared the failures with what the physics makes equal: the joint limits are symmetric, so a one-sided failure points to the policy, not the robot.
  • fecc7566 replayed its policy on 12 mirrored target pairs from identical states, 24 episodes, and saw at once that the negative-side command was not the mirror of the positive one.
  • The losing PIs explained failures by the shoulder limit or the arm configuration, which apply equally to the mirrored side that succeeds, and repeated the same mechanism question (five times in 7b4769e9). This led to OI-056.
Plateau

Tuning at about 97.5% cannot be measured

  • Without a structural change, PIs tuned reward, sampling and inputs and compared them on 400-episode panels, whose noise (about ±1.4 points) hides the 0.5-1 point gains being tested. Most comparisons tied.
  • All 30 training runs of round 1 used exactly 120k steps, although inquiry runs may use up to 360k.
  • The training seed alone moved the same recipe from 35% to 94%; with seed 0 all three round-1 campaigns produced the same first candidate (375/400).
First choice

An untested base anchors the campaign

  • 38ad68c6 changed two things in its first experiment: the radius range and joint targets with fixed-gain feedback. It scored 60%, never tested direct torque (about 94% elsewhere), applied the symmetry on that base and stopped at about 85%. This led to OI-055.
  • Joint targets with fixed-gain feedback stayed below direct torque in every campaign that tried them: 0 to 60% on first training, at most about 85% after further work. The gains were never checked before training, and no PI used a controller to generate demonstrations.
Decision

When to request the official assessment

  • Assessments requested at an estimated 40% (1d0fb8a9) and 64% (8ea728f4) pass chance failed at 195/200, one episode short.
  • 7b4769e9 had similar evidence, never requested an assessment and reached the AIU cap.
  • The winners requested the assessment after 400/400 on fresh panels, within minutes.
Cost

Diagnostics are paid by the coder and reviewer

  • Every diagnostic module is written by the coder and checked by the reviewer. In 38ad68c6 they used 54 of 123 AIU (44%), against about 20% elsewhere.
  • Round 4 showed the PI its elapsed time and AI usage by role (OI-054). Its PIs repeated the figures in almost every record, one requested the assessment after 1 h 47 at an estimated 41% pass chance, and none passed. The line was removed on 27 October, as earlier cost guidance had been on 20 October.

Model roles need an explicit assignment

Working: the candidate in use now.

Development and official results

Development measurements inform the PI. They do not declare the goal reached.

The official assessment needs goal review, no active inquiry, and an assigned best-known candidate.

Terms

Scientific model
A document about the robot and task. It separates facts, consequences, and unknowns.
Learned policy
The controller that learning produced. It picks actions from observations.
Policy checkpoint
Saved model weights from a training run. It is not a scientific conclusion.
Session record
A written record of work, evidence, open questions, and the next direction. The checkpoint operation saves it.
Candidate and recipe
A candidate is a registered learned policy. The recipe is the code and settings that produced it.
Best-known policy
See model roles. It is not automatically ready for assessment.
Harness
The launcher, the Runner, the contracts, and the context that support the process.
Status words

Implemented means the code contains the change. Observation means a named campaign showed a result. Open means the problem remains. Proposal means the change needs approval.

Deferred means work waits. Withdrawn means the change was removed. Historical means the entry describes an old state.
